# Cursor / TRAE 状态监控扩展分析

> 文档状态：Cursor 第一阶段与审批近似识别已实现；TRAE 仍为方案分析  
> 更新日期：2026-09-01

> 实现说明：项目现已增加独立的 `providers/codex.rs`、`providers/cursor.rs` 适配器、多活动存储、Provider 级退出清理，以及 Codex/Cursor Hooks 的安装卸载。本文中 Cursor 部分保留为设计依据，TRAE 部分尚未实现。

## 1. 背景与目标

Harbor Light 当前通过 Codex Hooks、会话 JSONL 和应用进程状态，将对话状态显示为红黄绿悬浮灯：

- 🟡 工作中：模型正在思考、生成或执行工具。
- 🔴 等待处理：任务需要用户确认或发生需要关注的异常。
- 🟢 已完成：本轮任务已经正常完成或被用户终止。
- ⚪ 空闲：当前没有活动任务。

如果进一步支持 Cursor 和 TRAE，目标不应只是检测软件是否启动，而是尽量准确回答以下问题：

1. 哪个软件、项目和对话正在执行？
2. 模型是否已经完成、被手动停止或异常终止？
3. 是否正在等待用户确认？
4. 多个软件和多个项目并行执行时，最终应该显示哪种灯光？
5. 某个软件退出时，如何只清理它自己的活动状态？

## 2. 总体结论

| 项目 | Cursor | TRAE |
| --- | --- | --- |
| 接入可行性 | 高 | 中，需先验证 Hook 协议 |
| 开始执行 | 可通过官方 Hook 准确识别 | 官方已支持 Hooks，但事件尚待验证 |
| 正常完成 | 可通过 `stop` / `sessionEnd` 识别 | 待验证 |
| 手动停止 | 可通过停止原因识别 | 待验证 |
| 等待权限 | 没有明确的权限弹窗事件 | 官方资料暂未明确 |
| 多项目并发 | Hook 提供会话和工作区标识 | 取决于 Hook 是否提供稳定标识 |
| 软件退出复位 | 可监听 Cursor 进程 | 可监听 TRAE 进程 |
| 建议定位 | 稳定支持 | 完成协议验证后再决定稳定版或 Beta |

结论如下：

- Cursor 已具备较完整的官方 Hooks，可以作为下一阶段的正式支持目标。
- TRAE 官方已加入 Hooks，但公开资料不足，不能直接假设其事件和 Cursor 兼容。
- 接入任何新软件前，都应该先将当前“单状态快照”改为“多来源、多活动聚合”模型，否则多个项目同时执行时会互相覆盖状态。

## 3. Cursor 监控方案

Cursor 官方 Hooks 支持通过标准输入接收 JSON，并公开了会话、模型、工作区和事件等信息。用户级配置文件为 `~/.cursor/hooks.json`，项目级配置文件为 `<project>/.cursor/hooks.json`。

参考：[Cursor Hooks 官方文档](https://prod.cursor.com/docs/hooks)

### 3.1 推荐事件映射

| Cursor 事件 | 建议处理 | 说明 |
| --- | --- | --- |
| `beforeSubmitPrompt` | 设置为 🟡 Working | 用户已提交提示词，是可靠的本轮开始信号 |
| `stop(completed)` | 设置为 🟢 Done | 正常完成，短暂显示后移除活动 |
| `stop(aborted)` | 设置为 🟢 Done | 用户手动停止，不能继续停在黄灯 |
| `stop(error)` | 设置为 🔴 Waiting/Attention | 表示任务异常，需要用户关注 |
| `sessionEnd` | 清理该会话 | 可处理关闭、主动中止、错误和窗口关闭 |
| `sessionStart` | 只登记会话，不亮黄灯 | 创建 Composer 对话不等于任务开始 |
| `preToolUse` | 只作为活动心跳 | 所有工具都可能触发，不能直接视为等待确认 |
| `afterAgentThought` | 只作为活动心跳 | 续期任务，防止长任务被误判为过期 |
| `afterAgentResponse` | 可记录响应节点 | 不建议单独作为最终完成信号 |

### 3.2 多项目和多对话

Cursor Hook 提供的以下字段有利于并发监控：

- `conversation_id`：区分不同对话。
- `generation_id`：区分同一对话中的不同轮次。
- `workspace_roots`：识别任务所属项目。
- `model` / `model_id`：记录实际模型来源。
- `transcript_path`：在必要时辅助诊断，但不应默认读取对话内容。

建议使用 `provider + conversation_id + generation_id` 作为活动键。不能只按软件进程或项目路径区分，因为同一项目也可能同时运行多个对话。

### 3.3 红灯语义限制与当前实现

Cursor 当前公开的 Hooks 中，没有一个明确表示“权限确认弹窗已经显示，正在等待用户”的专用事件。

不能把 `preToolUse` 直接映射为红灯，因为自动批准的工具同样会触发它，这会造成大量误报。可以采用以下语义：

- 黄灯、绿灯作为 Cursor 的稳定能力。
- `beforeShellExecution(sandbox=false)` 作为本机 Shell 审批的近似信号；`afterShellExecution` 或 `afterAgentThought` 恢复黄灯。
- 红灯也表示 `stop(error)` 或其他需要用户关注的异常。
- 由于 allowlist/自动批准信息没有完整暴露，自动批准的非沙箱命令可能短暂误亮红灯；如果未来 Cursor 提供明确权限事件，应替换此近似逻辑。

不建议以 UI 自动化识别权限窗口作为正式方案。这种方式依赖窗口标题和辅助功能树，升级后容易失效，同时会增加辅助功能权限和隐私成本。

### 3.4 Cursor Cloud Agent

Cursor Cloud Agent 不执行本机用户级 Hooks。若未来需要监控云端任务，需要将项目级 Hook 安装到每个目标仓库，并单独验证云端事件是否覆盖任务的完整生命周期。

因此，首版建议只承诺本地 Cursor 对话监控。

## 4. TRAE 监控方案

TRAE 官方更新日志显示，3.5.66 版本已加入 Hooks，并可通过 `Settings → Hooks` 进行配置。

参考：[TRAE 官方更新日志](https://www.trae.ai/ja/changelog)

但是，目前公开资料尚不足以确认以下关键能力：

- Hook 的完整事件列表。
- 标准输入 JSON 的字段格式。
- 是否提供稳定的会话、轮次和工作区标识。
- 是否能区分正常完成、手动停止和异常结束。
- 是否存在权限确认或等待用户的事件。
- 普通对话、SOLO、子代理是否使用相同协议。

因此，不能直接复用 Cursor 的配置和事件名称，也不应根据 TRAE 的内部目录或数据库格式推测生命周期。

### 4.1 建议先做协议采样

正式开发 TRAE 适配器前，应先配置一个被动 Hook。该 Hook 只记录 TRAE 传入的事件名称和结构，不修改 TRAE 行为，也不读取或上传对话正文。

需要覆盖以下测试场景：

1. 提交普通提示词。
2. 模型正常完成。
3. 回答过程中手动停止。
4. 工具自动执行。
5. 工具需要用户确认。
6. 模型或工具执行报错。
7. 关闭当前对话。
8. 直接退出或强制结束 TRAE。
9. 两个项目同时运行。
10. 同一个项目打开两个并行对话。
11. SOLO 或子代理任务。

采样后重点确认：

- 哪个事件是真正的任务开始和任务结束信号。
- 是否存在 `conversation_id`、`task_id` 或类似稳定 ID。
- 同一轮任务的事件能否可靠关联。
- 工作区字段是否能定位到项目。
- 软件异常退出时是否仍会发送结束事件。

若 Hook 能提供这些字段，TRAE 可以使用与 Cursor 相同的标准化适配层；若不能，则只能作为有限支持或 Beta 功能。

### 4.2 不建议依赖内部数据文件

不建议将 TRAE 的 SQLite、`globalStorage`、日志或缓存文件作为主要状态源：

- 内部格式可能随版本更新变化。
- 文件可能包含完整提示词、回复和项目敏感信息。
- 很难区分“任务正在执行”和“历史记录刚刚写入”。
- Windows 与 macOS 的内部目录和锁文件行为可能不同。

进程检测只适合作为退出清理兜底，无法单独判断一轮回答是否已经完成。

## 5. 当前架构需要调整的部分

### 5.1 单状态文件无法支持并发

当前实现将状态写入单个 `.codex-status.json`。这属于最后写入者覆盖前一个状态，无法表达多个同时存在的活动。

例如：

1. Codex 项目 A 正在运行，灯为黄灯。
2. Cursor 项目 B 完成，写入绿灯。
3. Cursor 的完成状态覆盖 Codex 的工作状态。
4. 界面显示绿灯，但 Codex 项目 A 实际仍在执行。

接入 Cursor 或 TRAE 前，应先改为每个活动独立存储，或使用能够表达多行活动记录的数据结构。

### 5.2 建议的统一活动模型

```text
provider: codex | cursor | trae
activity_id: provider 内唯一活动 ID
conversation_id: 对话 ID
generation_id: 本轮生成 ID，可选
workspace: 项目路径或显示名称
state: working | waiting | done
event: 最近一次原始事件
updated_at: 最近活动时间
background: 是否为后台或云端任务
```

建议优先选择以下存储方式之一：

1. 每个活动一个原子 JSON 文件，例如：

   ```text
   ~/.harbor-light/activities/<provider>/<activity-id>.json
   ```

2. 使用 SQLite 保存活动和事件。

活动文件方案更容易延续当前实现，跨进程写入时也不会因为共享一个文件而互相覆盖；SQLite 更适合未来查询历史和统计，但实现复杂度更高。首版建议使用独立活动文件。

### 5.3 聚合规则

悬浮窗仍然可以只显示一组红黄绿灯，但其状态必须由所有活动共同计算：

```text
Waiting > Working > Done > Idle
```

具体规则：

- 任何活动处于 Waiting，显示红灯。
- 没有 Waiting，但至少一个活动处于 Working，显示黄灯。
- 没有 Waiting/Working，但有刚完成的活动，短暂显示绿灯。
- 所有活动都结束或过期，显示空闲。
- Done 应按活动独立显示约 3 秒，之后删除或转为空闲。
- 心跳和过期时间应按活动更新，不能全局续期。

### 5.4 按软件清理状态

软件退出时不能进行全局复位，只能清理对应 Provider：

- Codex 退出：清理 Codex 活动。
- Cursor 退出：清理 Cursor 活动。
- TRAE 退出：清理 TRAE 活动。

否则，退出 Cursor 可能把仍在执行的 Codex 任务一起清掉。

macOS 可以按应用 Bundle ID 监听终止事件；Windows 可以分别记录各软件进程的运行状态。实际进程名和 Bundle ID 应在开发时通过安装后的正式版本确认，不能仅凭产品名称硬编码。

## 6. 界面与交互影响

只有一组聚合灯时，用户可以知道“有任务正在执行”或“某个任务需要处理”，但无法知道具体来自哪个软件和项目。

建议保持悬浮窗简洁，同时在菜单栏、系统托盘或提示信息中增加活动列表，例如：

```text
🔴 Cursor / project-a / 需要关注
🟡 Codex / project-b / 正在执行
🟢 TRAE / project-c / 刚刚完成
```

可以进一步支持：

- 点击活动项切换到对应软件。
- 显示项目名而不是完整路径，避免泄露目录信息。
- 对相同软件的多个活动进行分组。
- 在托盘中提供“仅清理过期活动”，而不是全局重置。

产品已从 `Codex Light` 更名为 `Harbor Light`，以便同时覆盖 Codex、Cursor 以及后续可能接入的其他 AI 编程工具。

## 7. macOS 与 Windows 打包影响

### 7.1 Hook 安装器

安装和卸载流程需要从“只管理 Codex Hook”扩展为“按 Provider 管理 Hook”：

- 安装时合并配置，不能覆盖用户已有 Hooks。
- 卸载时只删除本软件写入的 Hook 项。
- Cursor 用户级 Hook 和项目级 Hook 应分开处理。
- TRAE 在协议和配置位置确认前，不应自动写入配置。
- 不同 Provider 的 Hook 命令都应调用同一个可执行文件，并携带或推断 Provider。

### 7.2 进程监控

macOS 和 Windows 都需要维护独立的 Provider 运行状态，不能继续使用单一的 `codex_was_running` 或全局重置时间。

每个 Provider 至少需要：

```text
provider
process/bundle identifier
was_running
last_exit_at
```

进程退出只负责兜底清理。正常任务结束仍应以 Hook 生命周期事件为准。

### 7.3 打包与权限

Hook 适配本身不需要把 Cursor 或 TRAE 打包进安装程序，只需要安装 Harbor Light 可执行文件并配置对方的 Hooks。

需要额外考虑：

- Windows 安装路径中包含空格时的命令转义。
- macOS App Bundle 内实际可执行文件的绝对路径。
- 软件升级后 Hook 路径保持稳定。
- 卸载或迁移安装目录后清理旧 Hook。
- 不默认请求辅助功能、屏幕录制等高权限；只有采用 UI 自动化时才需要，而当前不建议采用。

## 8. 推荐实施顺序

### 阶段一：重构活动模型

- 引入 `Provider` 和 `Activity`。
- 将单状态快照替换为多活动存储。
- 实现统一优先级聚合。
- 改为按 Provider 清理。
- 补充多活动并发、过期和退出测试。

### 阶段二：支持 Cursor

- 增加 Cursor Hook 输入适配器。
- 安装和卸载用户级 Cursor Hooks。
- 映射开始、完成、中止、错误和会话关闭。
- 增加 Cursor 进程退出清理。
- 在托盘中显示软件和项目来源。

### 阶段三：验证 TRAE

- 使用最新版 TRAE 采样 Hook 协议。
- 完成完整场景测试矩阵。
- 确定 ID、工作区和结束语义。
- 根据结果决定正式支持、有限支持或 Beta。

### 阶段四：完善多平台交付

- 更新 macOS pkg 和 Windows 安装器。
- 在升级与卸载时正确合并、迁移和清理 Hooks。
- 补充 macOS 多应用退出和 Windows 多进程测试。
- 更新 README、排查说明和隐私声明。

## 9. 风险与验收标准

### 9.1 主要风险

- 将普通工具调用误判成权限等待，导致红灯频繁误报。
- 一个任务完成后覆盖另一个仍在运行的任务。
- 某个软件退出时误清理其他软件的活动。
- Hook 未发送结束事件，活动长期停在黄灯。
- TRAE 协议升级导致适配器失效。
- 读取内部会话文件造成隐私风险。

### 9.2 基础验收标准

完成多软件支持后，至少应满足：

1. Codex 和 Cursor 同时执行时，任一任务仍在工作就不能错误显示空闲或完成。
2. 一个对话手动停止后，不会一直停在黄灯。
3. 退出 Cursor 只清理 Cursor 活动，不影响 Codex/TRAE。
4. 两个项目同时运行时，托盘能够列出各自来源。
5. 过期清理针对单个活动，不进行全局复位。
6. Hook 安装不会覆盖用户已有配置，卸载只删除本软件的条目。
7. 不读取或上传完整对话内容即可完成状态判断。

## 10. 最终建议

Cursor 可以直接进入正式设计和实现阶段，但前置条件是先完成多活动存储与聚合重构。

TRAE 应先进行一次范围明确的 Hook 协议验证。验证通过后，再接入统一 Provider 适配层；如果无法获得稳定的会话 ID 或结束事件，应明确标记为有限支持，而不是通过读取内部数据库或 UI 自动化强行实现。

推荐的产品路线是：

```text
多活动架构重构 → Cursor 稳定支持 → TRAE 协议验证 → TRAE 分级支持 → 完善多平台安装包
```
